[deepseek-harness]微信聊天记录提取与分析

发表于 2026-08-22 分类于 Project ， Python

0x00 前言

微信聊天记录属于个人数字资产的一部分，但导出和留存一直不太方便。网络上有一个开源项目 LifeArchiveProject/WeChatDataAnalysis（官网：https://lifearchiveproject.github.io/WeChatDataAnalysis/），解决了微信本地数据库的读取与解密问题，理念是"你的微信数据，由你留存"。

本文记录的项目 Wechat Unsaid AI 就是基于这套方案构建的独立服务：读取微信本机数据库 → 筛选会话 / 时间 / 消息类型 → 导出 html / json / txt / excel → 打包 zip，并附带网页版聊天查看与 AI 分析。取密钥、进程内存扫描等基础能力参考主项目方案，本项目专注”导出与分析”这条链路。

0x01 项目简介

一句话概括：一个可独立运行的微信聊天记录导出与分析服务。

  • 后端：FastAPI，导出 API 契约与主项目 /api/chat/exports* 完全一致，前端组件无需改动即可对接
  • 双数据源：实时直读微信 WCDB（realtime / auto）与已解密 SQLite 库（decrypted）
  • 网页版：聊天记录查看、逐日趋势统计、可选接入 OpenAI 兼容大模型做 AI 分析
  • 多格式导出：HTML / JSON / TXT / Excel，支持媒体打包、隐私模式、WEC1 加密

0x02 构建逻辑（整体架构）

提取原则

从主项目提取时定了一条原则：只保留导出链路需要的东西，其余一律裁掉。

裁掉 原因
解密 / 密钥提取（pymem / wx_key / 进程扫描） 导出只读已解密库或实时可读库，不做解密
朋友圈 / 年度总结 / MCP / 公众号 不属于导出链路
桌面壳 Electron / 主项目前端页面 本服务为纯后端，网页版另外写
语音转写（faster-whisper，约 1GB 模型） 可选能力，需要时自行安装

双数据源设计

这是整个构建逻辑里最关键的一个决策：

  • realtime / auto（实时直读）：直接读微信本机 WCDB 原始库，依赖 native/ 下的原生组件（VoipEngine.dll、wechatdb_broker.exe 等）与数据库密钥
  • decrypted（已解密库）：读 output/decrypted 下的已解密 SQLite 库，纯 Python 实现，不依赖 DLL 与密钥

原生组件缺失时自动降级到已解密库，导出功能不受影响。decrypted 路径纯粹由 Python 实现，跨平台移植性最好，也为后续移动端部署留了路。

导出核心

导出由 chat_export_service.py（CHAT_EXPORT_MANAGER）承载，是一个完整的异步任务模型：

方法 路径 说明
POST /api/chat/exports 创建导出任务（zip），支持 html / json / txt / excel、scope、时间 / 类型过滤、媒体打包、隐私模式、WEC1 加密
GET /api/chat/exports 列出导出任务
GET /api/chat/exports/targets 导出目标（会话）预览
GET /api/chat/exports/{id} 任务状态
GET /api/chat/exports/{id}/download 下载 zip
GET /api/chat/exports/{id}/events 任务进度 SSE
DELETE /api/chat/exports/{id} 取消任务

大文件导出采用后台任务 + SSE 进度推送，前端可以实时看到进度而不用轮询，这一块是构建时比较顺手的部分。

0x04 网页版与 AI 分析

聊天查看

网页版是静态页面，由 FastAPI 在同进程托管。左侧会话列表（昵称 / 最后消息预览），按日期浏览消息，支持前后翻页与日期选择。

统计分析

统计全部是本地确定性计算，不依赖任何外部服务：

  • 单日视角：消息频次（按时段）、聊天发起人（静默间隔后谁先开口）、回复延迟（平均 / 中位）、双方消息数 / 字数 / 表情 / 短回复对比
  • 全日期视角：逐日趋势折线图，我 vs 对方双线对比

AI 分析（可选）

在「AI 设置」填入 OpenAI 兼容接口（endpoint / API Key / 模型，如 DeepSeek），由浏览器直接调用，Key 只保存在本机浏览器 localStorage，不经过服务端。不配置时仅显示规则统计。

网页版接口：

方法 路径 说明
GET /api/view/accounts 账号列表（含密钥 / 解密状态）
GET /api/view/wechat-status 微信安装与账号自动探测
POST /api/view/decrypt 一键自动处理（取密钥 + 解密）
GET /api/view/accounts/{account}/contacts 会话 / 联系人列表
GET /api/view/messages 按日期读取消息
GET /api/analysis/day 单日统计
GET /api/analysis/all 全日期趋势

0x05 关键取舍与踩坑

构建过程里几个值得记录的决策点：

  1. 接口契约对齐主项目：/api/chat/exports* 完全照搬契约，好处是主项目前端组件（ChatExportDialog.vue / useChatExport.js）可以零改动对接，两边可以互相替换。
  2. 降级优先于报错：原生组件缺失时不直接 500，而是降级到已解密数据源，服务始终可用。
  3. 端口冲突：主项目后端也常用 10392，独立版必须支持端口覆盖，最终用 STANDALONE_EXPORT_PORT 环境变量解决。
  4. 隐私与合规：账号密钥、导出 zip、output/ 目录全部进 .gitignore，仓库里不提交任何隐私文件；工具只用于处理本人持有或有权限访问的数据。
  5. 可选依赖分离：取密钥（pymem / wx_key / yara-python）与语音转写（faster-whisper）都标记为可选，基础导出功能不强制安装。

0x06 快速开始

启动：双击 start.bat，或 python main.py。

  • 网页版（聊天查看 + AI 分析）：http://127.0.0.1:10399/
  • 健康检查：http://127.0.0.1:10399/api/health
  • API 文档：http://127.0.0.1:10399/docs

0x07 总结

从主项目里拆出”导出与分析”这条链路，独立成一个能跑的服务，过程中比较满意的是三点：

  • decrypted 纯 Python 路径让导出核心不绑死在 Windows 上，后续如果要上手机（Chaquopy / Termux 跑 Python 核心）有现成路线
  • 接口契约对齐保住了与主项目前端的兼容性，相当于白拿了成熟的导出交互层
  • 降级设计让服务在组件不全的环境里依然可用

读取与解密部分再次感谢 LifeArchiveProject/WeChatDataAnalysis。项目代码在 https://github.com/wenbuer/wechat-unsaid-ai-web ，欢迎参考。
